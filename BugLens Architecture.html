BugLens architecture

A local assistant that answers questions about past Jira bugs and decides whether a release can ship. Nothing leaves the machine: the models, the vector store and the files all run locally.

  • branch: jira-integration
  • Ollama: llama3.1 + nomic-embed-text
  • ChromaDB, cosine, 768-d
  • Streamlit + MCP (stdio)

System overview

Two front doors, one engine. The Streamlit app and the MCP server both call straight into search.py, so retrieval, verification and the release gate exist once.

Ingestion and the embedding cache

Re-ingesting is cheap because only text that changed is embedded. The Chroma folder is still rebuilt from scratch every time, so it can never hold stale bugs.

What happens during one search

The person sees one answer. Underneath there is one embedding call, one Chroma query, one verification call per candidate bug, and one writing call.

Release gate

The GO or NO-GO decision is a few lines of Python. The model is given the verdict and asked to explain it.

Who decides what

The boundary between the model and Python is the main design decision. Anything the model got wrong in testing was moved to code.

DecisionMade byWhy it sits there
Which bugs look similar to the questionembeddings + BM25That is what they are built for.
Is a retrieved bug really about the same problemLLM, one call per bugA judgment call. Each bug is checked on its own so one cannot sway another.
Duplicate or merely relatedLLM then similarity floor 0.75The model treats same component as same defect. A low-similarity "duplicate" with hedged wording is downgraded.
Relevance flag versus badge shownconsistency guardrailThe two fields are filled in separately and can disagree. "Not relevant" always wins.
Release GO or NO-GOPython ruleA gate that can hallucinate is not a gate.
Which bug IDs may be citedPython filterThe model invents IDs. Any ID not in the retrieved set is removed.
Counts and priority breakdowns in the textPythonThe model once swapped two counts in a live run.
The wording of every explanationLLMProse is the one thing it does well.

Keeping a running app in step with re-ingest

search.py keeps the collection and the BM25 index in memory. Ingest deletes and rebuilds the folder underneath them, so a small marker file tells them to reload.

Data model

One bug travels through three shapes: a CSV row, a Chroma record, and a cache entry.

CSV row jira_bugs.csv

One row per Jira bug, written by jira_fetch.py. Same columns as sample_bugs.csv.

  • ID, Title, Description
  • Comments, Resolution
  • Component, Severity, Priority, Status
  • Created, ReleaseVersion

Chroma record collection "bugs"

Stored by ingest.py. The bug ID is the record ID.

  • embedding: 768 floats, cosine
  • document: Title, Component, Description, Comments, Resolution as one text
  • metadata: bug_id, title, component, severity, priority, status, release_version, resolution (first 500 chars), created

Cache entry embedding_cache.json

Speeds up re-ingest. It never serves queries.

  • key: sha256 of model name + document text
  • value: the 768-float vector
  • Pruned each run to the bugs just ingested, so it never outgrows the bug count
