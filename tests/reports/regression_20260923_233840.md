### has our refund process had any silent failures?
*29.7s — PASS*

> Yes, there have been silent failures in the refund process. According to Bug [SCRUM-28], when a support agent issues a partial refund above $500, the API returns 200 but no refund is actually created in the payment processor (Stripe). This has resulted in 4 customers being affected so far this week.

The root cause of this issue was that Stripe's refund.created webhook never fires for these cases. The resolution involved investigating and confirming the problem through production logs.

Additionally, Bug [SCRUM-53] also indicates a silent failure in the refund process, specifically for orders paid via Apple Pay. Refunds initiated for these orders fail with a generic error, while card-paid refunds work fine. This was due to Apple Pay tokens requiring a different, dedicated refund endpoint that hadn't been wired up. The resolution involved routing Apple Pay refunds through the correct token-based refund endpoint.

Both of these bugs indicate silent failures in the refund process, where the API returns success but no actual refund is created or processed correctly.

> The root cause of the memory leak in the worker service was that the pdf-lib library was creating Document instances per request without disposing of them, causing a gradual increase in memory usage over time. This issue was fixed by wrapping PDF processing in a try/finally block with explicit doc.unload() calls to ensure proper disposal of resources. Additionally, a pod memory alert was added at 80% and the approach for processing large files (>10MB) was switched to streaming.

### what caused the database connection pool issue?

This caused the pool to become exhausted, leading to unrelated requests across the app timing out.
